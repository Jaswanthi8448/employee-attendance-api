# REVIEW.md

Defects found in the starter `app/main.py`. Line numbers refer to the original starter.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `MongoClient(...)` L22 | No `tz_aware=True`: PyMongo returns naive datetimes, which then get mixed with aware ones (`compute_overtime` builds an IST-aware `end`). | `punch_out - end` raises `TypeError: can't subtract offset-naive and offset-aware` and you get a 500. | `tz_aware=True` gives aware UTC datetimes everywhere. Also `serverSelectionTimeoutMS=5000`. |
| 2 | module level | No indexes are created at startup, so there is no unique constraint and every list or analytics query does a COLLSCAN. | `/admin/explain` shows COLLSCAN, and duplicates appear under load. | `ensure_indexes()` runs in the lifespan hook. It is idempotent. |
| 3 | `compute_late_minutes` L33-37 | The grace check runs on truncated whole minutes (`minutes > 10`), so 09:40:59 counts as 10 minutes, which is "not > 10", so 0. R2 says *strictly more than 10:00*. | Shift 09:30, punch 09:40:01 returns 0 (expected 10); 09:40:59 returns 0. | Compare seconds against 600 (`seconds > 600`), then floor the minutes. |
| 4 | `compute_late_minutes` L35 | `punch_in.replace(hour=h, minute=m)` sets the shift start in the punch's own time zone (UTC or server-local), not IST. | 09:28 IST is 03:58 UTC. Comparing it with 09:30 "UTC" gives the wrong late minutes on any non-IST server. | The shift start is built with `datetime.combine(attendance_date, shift_start, IST)`. |
| 5 | `compute_late_minutes` | Not anchored to the attendance date, so overnight shifts break. A 00:30 punch for a 22:00 shift is compared with 22:00 of the *same* calendar day. | Overnight employee, punch 00:30 IST returns 0 (expected 150). | The shift start is taken from the R1 attendance date. |
| 6 | `compute_work_hours` L41 | Python `round()` is binary-float, half-to-even rounding, not half-up (R4). It also skips the R1 truncation to whole seconds. | 4 h 29 m 42 s = 4.495 h gives `round(4.495, 2)` = 4.49, so `half_day` flips to true. | `Decimal(seconds)/3600` quantized with `ROUND_HALF_UP` on second-truncated instants. |
| 7 | `compute_overtime` L44-47 | The 30-minute minimum (R3) is missing, so 5 minutes past the shift end counts as overtime. | Out at 18:35 gives 5 (expected 0). | `minutes if minutes >= 30 else 0`. |
| 8 | `compute_overtime` L46 | For overnight shifts the end is put on `date_str` instead of the next day. | Shift 22:00-06:00, out 06:40 next day gives 1480 (expected 40). | `shift_end_at` adds a day when `shift_end <= shift_start`. |
| 9 | `EmployeeIn` L53-60 | No validation: `emp_code` pattern, email, `HH:MM`, real calendar `joined_on`, lengths, and `shift_start != shift_end` are all unchecked. | `{"shift_start": "25:99"}` or `{"joined_on": "2026-02-30"}` is stored, and later the helpers crash with a 500. | Pydantic constraints (patterns, lengths, a date validator) plus a model validator for equal shift times. |
| 10 | `PunchInIn` L63-66 | `punched_at: Optional[int]` uses lax mode, so it accepts `"1783312500000"`, `1783312500000.0` and seconds-looking values. `status: str` accepts `ABSENT` or any string. | A punch with `punched_at=1783312500` (seconds) lands in 1970. `status="ABSENT"` is accepted at punch-in. | `EpochMillis = Annotated[int, Field(strict=True, ge=1e11, le=4102444800000)]` and `status: Literal["PRESENT","WFH","ON_DUTY"]`. |
| 11 | `health` L72-74 | Always returns 200, even when MongoDB is down. | Stop mongod: `/health` still says ok. | Pings MongoDB and returns 503 on failure. |
| 12 | `create_employee` L79-80 | Check-then-insert race: two concurrent creates both pass `find_one` and both insert. | 8 parallel POSTs with the same `emp_code` give several 201s. | A unique index on `emp_code`. Insert and map `DuplicateKeyError` to 409. |
| 13 | `create_employee` L82 | `created_at = datetime.now()` is naive server-local time (stored as if it were UTC), and it is returned as an ISO string, not epoch ms. | On an IST server `created_at` is off by 5.5 h, and the response type does not match the contract. | `datetime.now(UTC)` truncated to ms, serialized to epoch ms. |
| 14 | `list_employees` L93 | `skip = page * page_size` skips the first page. | `page=1` returns employees 21-40. | `(page - 1) * page_size`. |
| 15 | `list_employees` L94 | `total` counts the whole collection, ignoring the `department` filter (R10). | `?department=Sales` gives total = all employees. | `count_documents(query)`. |
| 16 | `list_employees` L95 | No sort. The order is undefined, but the contract requires `emp_code` ascending. | Pages are unstable after inserts or deletes. | `.sort("emp_code", 1)` backed by an index. |
| 17 | `list_employees` / `list_attendance` params | `page` and `page_size` are unvalidated. `page=0` gives a negative skip and a 500; `page_size=0` means "no limit"; there is no max of 100. | `GET /employees?page=0` returns 500. | `Query(ge=1)` and `Query(ge=1, le=100)`, so bad values get 422. |
| 18 | `list_employees` | `created_at` is returned as a datetime, not epoch ms. | The response has an ISO string. | `serialize_employee`. |
| 19 | `punch_in` L100-112 | Unknown employee: `emp` is `None` and `emp["shift_start"]` raises `TypeError`, giving a 500 instead of 404. | `POST /attendance/punch-in {"emp_code":"EMP9999"}` returns 500. | Look up the employee and return 404 when it is missing. |
| 20 | `punch_in` L101 | `datetime.fromtimestamp(ms/1000)` and `datetime.now()` use the *server's local* time zone and naive datetimes. The date is therefore not the IST date (R1), and the milliseconds are not truncated. | A punch at 01:00 IST on a UTC server gets the previous day's date. 09:40:00.900 is treated as later than 09:40:00. | `EPOCH + timedelta(seconds=ms // 1000)`, aware UTC. The date is computed in IST. |
| 21 | `punch_in` L102 | The R1 overnight rule is missing: a 00:30 punch on a 22:00-06:00 shift gets the wrong date. | Overnight punch at 00:30 on 07-07 is stored as 07-07 (expected 07-06). | `attendance_date()` moves early-morning punches of overnight shifts back one day. |
| 22 | `punch_in` L103-104 | Check-then-insert race, so two identical concurrent punch-ins both get 201 and create duplicates. | 10 parallel identical punch-ins give several 201s. | A unique index on `(emp_code, date)`. Insert directly and map `DuplicateKeyError` to 409. |
| 23 | `punch_in` L118-120 | The response leaks the internal `_id` as `id`, and `punch_in` is a datetime, not epoch ms. | The response has an `"id"` field and an ISO timestamp. | `serialize_record` returns exactly the contract fields. |
| 24 | `list_attendance` L141-147 | `find(q)` loads every matching document into memory and sorts in Python. That is O(n) memory and slow at 100k records. There is also no `emp_code` tiebreaker in the sort. | Latency grows with collection size, and same-date rows come back in random order. | DB-side `.sort([date -1, emp_code 1]).skip().limit()` on the `(date, emp_code)` index, plus `count_documents` for `total`. |
| 25 | `list_attendance` | No validation: `date_from > date_to`, malformed dates and unknown statuses are all accepted. | `?date_from=2026-07-08&date_to=2026-07-01` returns 200 and an empty list (expected 422). | Date pattern plus a real-date validator, a `Status` literal, and an order check. |
| 26 | `list_attendance` L146-147 | Leaks `_id` as `id`. Datetimes are not converted to ms. Legacy records missing `history` / `half_day` are returned without them. | Sample record #9 is returned without `history`. | `serialize_record` fills in the documented defaults. |

**Looked at and judged not a defect**
- `load_dotenv()` uses `override=False` by default, so real environment variables already take priority over `.env`.
- `doc.pop("_id", None)` after `insert_one` in `create_employee` is correct. `insert_one` mutates the dict to add `_id`, so it does have to be removed before returning.
- `compute_work_hours` itself (out minus in, in hours) is the right formula. Only the rounding and truncation were wrong.
- `int(...)` truncation in `compute_overtime` behaves like floor for positive values. It is wrong only for negative values, which are then clamped to 0 anyway.
